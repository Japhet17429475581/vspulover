# люблю | ВГСПУ — Telegram-предложка

Бот принимает анонимные предложения, показывает окончательный текст автору и сохраняет его только после подтверждения. Администраторы одобряют или отклоняют предложения в личном чате с ботом.

**Публикация реализована.** При `PUBLICATION_ENABLED=true` новые одобренные предложения автоматически отправляются в `CHANNEL_ID` через постоянную очередь. После успешной отправки статус становится `published`, сохраняются дата и Telegram message ID. По умолчанию публикация выключена, пока не настроен канал. Исходящие запросы разрешены в личные чаты и только в явно настроенный канал.

## Быстрый запуск

Нужны Python 3.11+, доступная PostgreSQL и токен от [@BotFather](https://t.me/BotFather). Запускайте команды из корня проекта. PostgreSQL уже может использоваться другими приложениями: бот создаёт отдельную схему `love_bot` вместе со своей таблицей версий Alembic.

Linux:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install --require-hashes -r requirements.txt
python -m pip install --no-deps -e .
cp .env.example .env
```

Windows PowerShell:

```powershell
py -3.12 -m venv .venv
.venv\Scripts\python.exe -m pip install --require-hashes -r requirements.txt
.venv\Scripts\python.exe -m pip install --no-deps -e .
Copy-Item .env.example .env
```

Заполните `.env`:

```dotenv
BOT_TOKEN=ваш_токен
DATABASE_URL=postgresql+asyncpg://bot_user:ваш_пароль@db.example.org:5432/existing_database
ADMIN_IDS=ваш_числовой_Telegram_ID
AUTO_APPROVE_ENABLED=false
CHANNEL_ID=-1001234567890
PUBLICATION_ENABLED=true
PUBLICATION_INTERVAL_SECONDS=60
```

`ADMIN_IDS` принимает `123456789,987654321` или `[123456789,987654321]`. Нужны **числовые ID личных аккаунтов**, а не username, ID бота или отрицательный ID группы. Свой ID можно получить через `getUpdates` Telegram Bot API после сообщения боту; не передавайте никому токен. Каждый администратор должен открыть бота и нажать `/start`, иначе Telegram не разрешит боту первым отправлять ему уведомления.

После заполнения переменных:

```bash
alembic upgrade head
python -m love_bot
```

В PowerShell без активации окружения:

```powershell
.venv\Scripts\alembic.exe upgrade head
.venv\Scripts\python.exe -m love_bot
```

Откройте бота: `/start` → `♡ предложить` → текст → предпросмотр → `♡ отправить`. У администратора: `/admin` → `📥 очередь` → решение. `/cancel` отменяет текущий черновик.

Добавьте бота в администраторы нужного **канала** и разрешите публикацию сообщений. Замените пример `CHANNEL_ID` своим числовым ID. При включённой публикации бот проверяет тип чата и свои права при запуске. Старые одобренные записи можно отправить кнопкой «📤 опубликовать» в карточке; включение режима само по себе не публикует весь старый архив. Подробнее: [PUBLICATION.md](PUBLICATION.md).

Бот работает через polling и при старте снимает существующий webhook, сохраняя накопленные обновления. Для одного токена нужен один polling-процесс ([документация aiogram](https://docs.aiogram.dev/en/latest/dispatcher/long_polling.html)). Дополнительно PostgreSQL advisory lock запрещает двум экземплярам одновременно обслуживать одну схему.

## PostgreSQL

`DATABASE_URL` поддерживает `postgres://`, `postgresql://` и `postgresql+asyncpg://`. Символы `@`, `:`, `/`, `#`, `%` в логине/пароле нужно percent-encode. Для TLS используйте, например, `?ssl=require`; `?sslmode=require` автоматически преобразуется для asyncpg. Если хостинг требует проверки сертификата, используйте `?ssl=verify-full` и настройте доверенный сертификат в окружении хостинга.

Для первой миграции пользователю PostgreSQL нужны `CONNECT` и право создать схему в этой базе. Схема `love_bot` должна быть свободна или уже принадлежать этому проекту. Если у пользователя нет `CREATE` на базу, владелец БД может заранее выполнить:

```sql
CREATE SCHEMA love_bot AUTHORIZATION bot_user;
```

Бот не создаёт и не удаляет саму базу, не использует `public.users` или другие чужие таблицы. Конфликт существующих объектов внутри `love_bot` приводит к ошибке миграции, а не к их перезаписи. Перед первым применением к рабочей БД сделайте резервную копию. Посмотреть SQL без подключения:

```bash
alembic upgrade head --sql
```

Основные таблицы:

| Таблица в схеме `love_bot` | Назначение |
| --- | --- |
| `bot_users` | Telegram ID, даты активности, согласие на уведомления, счётчик |
| `submissions` | Оригинальный и подтверждённый текст, статус, признаки, решение, сведения о проверке |
| `moderation_audit` | Переходы статусов, ID модератора, время и причина решения |
| `notification_outbox` | Надёжная очередь уведомлений после фиксации транзакции |
| `publication_jobs` | Постоянная очередь публикаций, попытки и результаты отправки |
| `publication_state` | Сохранённая пауза между постами |
| `alembic_version` | Независимая история миграций бота |

Дата/время в БД — UTC. Карточки и календарный показатель «за сегодня» используют `DISPLAY_TIMEZONE`, по умолчанию `Europe/Moscow`. «За 24 часа» — отдельное скользящее окно. Индексы покрывают статус, автора, время, проверку повторов и очередь уведомлений.

## Поведение и защита от повторов

- Нормализатор удаляет только самостоятельное начальное «люблю», включая кавычки и разделительную пунктуацию. Сохраняет регистр продолжения, эмодзи и разумные переносы строк. Не исправляет орфографию. Невидимые разделители и bidi-управление удаляются; emoji ZWJ сохраняется. Автор всегда видит результат.
- Пустой текст, текст без букв, длинные повторы, управляющие символы и окончательный текст длиннее лимита не принимаются. Только текст: фотографии, стикеры и подписи к ним не становятся предложениями.
- До подтверждения черновик живёт в памяти, обычно 30 минут. Перезапуск отменяет неотправленные черновики: пользователь создаёт новый. Подтверждённые предложения и очередь уведомлений находятся в PostgreSQL.
- UUID предпросмотра связывает кнопку с текущим черновиком. Старые кнопки не отправляют изменённый текст. Уникальный `request_key` в БД защищает от повторного сохранения.
- По умолчанию можно подтвердить 3 предложения за скользящий час. Одинаковый нормализованный текст того же автора, без учёта регистра и лишних пробелов, нельзя повторять в течение 24 часов. Блокировка строки автора делает проверки атомарными при параллельных запросах.
- Быстрые действия, включая команды и предпросмотры, дополнительно ограничены в памяти: запас 20 действий на пользователя, восстановление одного действия в секунду. При флуде лишние события молча пропускаются; технические ключи удаляются через 5 минут бездействия.
- Модераторские права проверяются на каждом callback и повторно в сервисном слое. Решение — условный `UPDATE ... WHERE status='pending'` в транзакции с аудитом и уведомлением. Из двух одновременных решений проходит одно.
- «Мои предложения» получает ID исключительно из Telegram-отправителя и показывает 10 последних собственных записей. Карточки модераторов не показывают авторский Telegram ID, имя или username.
- Тексты отправляются как обычный текст, без HTML/Markdown и предпросмотра ссылок. Пользовательский ввод не становится SQL или Telegram-разметкой.

## Модерация

`ModerationClassifier` возвращает `decision`, `confidence`, `reasons`, `flags`. Базовая реализация сочетает признаки ссылок, рекламы, контактов, конкретных людей, угроз, травли и необычного Unicode. Сложные и сомнительные случаи идут человеку. Правила не являются полноценным семантическим классификатором и не гарантируют распознавание всех обходов.

С `AUTO_APPROVE_ENABLED=false` все допустимые содержательные тексты становятся `pending`. После одобрения модератором они становятся `approved` и при включённой публикации ставятся в очередь канала. Очевидная реклама, приглашения, угрозы и раскрытие чужих контактов отклоняются на предварительном этапе: окончательная запись не создаётся. Такие попытки не входят в статистику отправленных предложений.

С `AUTO_APPROVE_ENABLED=true` только **точные** совпадения с пятью фразами могут стать `approved`: «маму и папу», «когда отменяют пары», «свою группу», «осенний Волгоград», «тёплый чай после пар». При включённой публикации такие записи тоже идут в канал. Дополнительный текст или подозрительные признаки исключают автоматическое одобрение. Проверка регистронезависима. Перед включением проверьте список на своих примерах.

Для правил `confidence=null`: совпадение со списком не выдаётся за вероятность. `AUTO_APPROVE_CONFIDENCE=0.95` зарезервирован для будущего проверенного классификатора. Никакие платные API, LLM, Redis или веб-админка не используются.

У модератора есть причины отклонения: спам, личные данные, оскорбление или травля, не подходит формату, другое. В карточке сохраняется нормализованный текст и причина. Автор получает только нейтральное сообщение. Кнопка «📤 публикации» показывает очередь и ошибки отправки; успешные посты учитываются в статистике и истории автора.

## Уведомления, данные и логи

После отправки бот подтверждает получение. Новые `pending` создают уведомления администраторам с кнопками очереди. Одобрение/отклонение создаёт уведомление автору, если оно включено. Настройка уведомлений доступна через «как это работает».

Outbox записывается в той же транзакции, что и решение. Ошибки Telegram не откатывают модерацию. Временные ошибки повторяются с задержкой, максимум 8 попыток; блокировка бота отключает уведомления автору. Устаревшие уведомления пропускаются. Доставка имеет семантику **как минимум один раз**: при аварии между ответом Telegram и фиксацией доставки возможно повторное уведомление, но повторного предложения или решения не будет.

Не собираются имена/username/телефоны из Telegram-профиля. Для очереди, истории и лимитов сохраняется связь Telegram ID с отправленными текстами. Это анонимность для читателей канала, а не сокрытие от владельца базы. Текст сам может содержать личные сведения; не присылайте чужие контакты.

Автоматическая очистка запускается при старте и затем каждый час:

- оригиналы удаляются через `ORIGINAL_TEXT_RETENTION_DAYS` (7 дней);
- технические уведомления удаляются через `TECHNICAL_RETENTION_DAYS` (7 дней);
- предложения, включая одобренные, и связанный аудит удаляются через `RETENTION_DAYS` (180 дней);
- неактивные пользователи без оставшихся предложений удаляются через тот же срок;
- неотправленные черновики и связанные технические ключи истекают по `DRAFT_TTL_SECONDS`.

Очистка обрабатывает авторов пачками и пропускает занятые транзакциями строки до следующего запуска. `/privacy` показывает фактические настроенные сроки. `/delete_my_data` требует отдельного подтверждения и удаляет **все** записи автора из базы, связанный аудит, профиль, уведомления и задания публикации. Ещё не отправленные посты отменяются. **Уже опубликованные посты остаются в канале**: для их удаления нужно обратиться к его администратору. Чужие предложения не затрагиваются. Удаление имеет приоритет над сохранением аудита. Старая карточка Telegram может остаться в истории, но кнопки больше не работают. Резервные копии и историю Telegram владелец обслуживает отдельно. Удаление данных также сбрасывает ограничения, рассчитанные по удалённым записям.

Статистика строится по реально оставшимся записям: пользователи, предложения, сутки/сегодня, статусы, доля автоматически обработанных, уникальные авторы за 7/30 дней. Это не пожизненная аналитика после удаления данных. Счётчик `bot_users.submissions_count` учитывает подтверждения за время существования профиля.

Логи — JSON в stderr: событие, уровень, время, тип ошибки. Полные тексты, токены, URL подключения, параметры SQL и traceback с пользовательским вводом не выводятся. Сообщения библиотек заменяются нейтральным кодом. Для длительного хранения настройте ротацию логов на хостинге.

Все переменные приведены в `.env.example`; значения реального окружения важнее `.env`.

## Тестирование

Установите зависимости разработки в активное окружение:

```bash
python -m pip install --require-hashes -r requirements-dev.txt
python -m pip install --no-deps -e .
ruff check src tests migrations
ruff format --check src tests migrations
pytest -q
```

Без `TEST_DATABASE_URL` интеграционные тесты помечаются пропущенными. Для полного прогона нужна **отдельная** база с именем, заканчивающимся на `_test`: тесты очищают таблицы бота только в ней. Не подставляйте рабочую базу.

Готовый одноразовый PostgreSQL:

```bash
docker compose -f compose.test.yml up -d --wait
export TEST_DATABASE_URL='postgresql+asyncpg://postgres:local_test_only@127.0.0.1:55439/love_bot_test'
pytest -q
docker compose -f compose.test.yml down
```

В PowerShell вместо `export`:

```powershell
$env:TEST_DATABASE_URL = 'postgresql+asyncpg://postgres:local_test_only@127.0.0.1:55439/love_bot_test'
.venv\Scripts\python.exe -m pytest -q
```

Тесты применяют настоящие миграции, проверяют соответствие моделей и сохранность чужой таблицы; запускают SQLAlchemy/asyncpg-транзакции, конкурирующие отправки и решения модераторов. Полные сценарии идут через `Dispatcher.feed_update` с настоящими Telegram-моделями. Подменяется только сетевой Telegram API: тесты не отправляют сообщения реальным людям. Проверяются также публикация подтверждённого текста, паузы, выключенный режим, права, повторные нажатия, сетевые сбои и сверка неизвестного результата, удаление, TTL и запрет посторонних адресов. GitHub Actions подготовлен для Python 3.11/3.12/3.13 и PostgreSQL 17.

## Linux и Bothost

Обычный Linux: установите проект в `/opt/love-bot`, создайте системного пользователя `lovebot`, выдайте ему чтение файлов проекта и защищённого `.env`. Шаблон `deploy/love-bot.service` запускает миграции перед ботом и перезапускает процесс при сбое. После проверки путей установите unit в systemd:

```bash
sudo cp deploy/love-bot.service /etc/systemd/system/love-bot.service
sudo systemctl daemon-reload
sudo systemctl enable --now love-bot
sudo journalctl -u love-bot -f
```

Docker:

```bash
docker build -t vgspu-love-bot .
docker run -d --name vgspu-love-bot --restart unless-stopped --env-file .env vgspu-love-bot
```

Внутри контейнера `localhost` означает сам контейнер. Укажите реальный доступный адрес PostgreSQL. `deploy/start.sh` выполняет миграции и через `exec` запускает бота. Образ работает от непривилегированного пользователя, а PostgreSQL остаётся внешней постоянной БД.

Для Bothost загрузите репозиторий с этим Dockerfile. В дополнительных настройках включите **«Использовать собственный Dockerfile»**, как описано в [документации Bothost](https://bothost.ru/docs/custom-dockerfile). Добавьте `BOT_TOKEN`, `DATABASE_URL`, `ADMIN_IDS` и остальные значения через [переменные окружения](https://bothost.ru/docs/environment-variables). Polling не требует веб-порта или домена. Используйте внешний доступный PostgreSQL; не храните его данные в файловой системе контейнера ([хранение БД на Bothost](https://bothost.ru/docs/database-storage)).

## Обновление без потери данных

1. Сделайте резервную копию PostgreSQL средствами владельца базы; сохраняйте её вне контейнера и репозитория. Не удаляйте схему/таблицы, `.env` или том PostgreSQL.
2. Остановите старый polling-процесс: `sudo systemctl stop love-bot` либо штатно через хостинг.
3. Обновите исходники. Установите новый `requirements.txt`, затем `python -m pip install --no-deps -e .`.
4. Выполните `alembic upgrade head`. Проверьте успешное завершение. При ошибке не запускайте новый бот и не применяйте `downgrade` к рабочим данным: он удаляет таблицы проекта.
5. Запустите сервис. Проверьте логи, `/admin` и существующую очередь. В Docker/Bothost миграцию выполняет стартовый скрипт.

Подтверждённые предложения, аудит, лимиты, уведомления и задания публикации переживают перезапуск; незавершённые черновики нужно ввести заново. Миграция `0002` добавляет очередь публикаций, сохраняя существующие записи. При изменении схемы используйте новые миграции; уже применённые миграции не редактируют.

## Структура

```text
src/love_bot/
  __main__.py          polling, жизненный цикл, очистка
  bot.py               aiogram handlers, FSM, предпросмотр и команды
  ui.py                русские тексты, кнопки, карточки
  text_normalizer.py   чистые функции форматирования и валидации
```

## Публикация в канал

Источник поста — только `normalized_text`, который автор подтвердил. Обработчик модерации фиксирует `approved` и задание в одной транзакции; отдельный worker публикует текст и сохраняет `published_at`, `channel_message_id`, статус `published` и аудит. Общая блокировка и сохранённая пауза защищают от конкурирующих отправок. При `429` выполняется отложенный повтор. При неизвестном результате запроса автоматический повтор останавливается до сверки администратором. Настройка, обработка ошибок и ограничения описаны в [PUBLICATION.md](PUBLICATION.md).
